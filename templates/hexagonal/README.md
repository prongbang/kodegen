# Hexagonal/Clean Architecture Overview


This project follows a **Hexagonal/Clean Architecture** with a clear composition root and one–way dependencies.

```
src/
 ├─ main.rs            # entrypoint (HTTP; also serves gRPC when GRPC_PORT is set)
 ├─ bootstrap.rs       # composition root (one builder per feature + grpc_routes)
 ├─ api/               # delivery layer: one module per feature —
 │                     #   <feature>.rs (axum routes) or <feature>_grpc.rs (tonic adapter)
 ├─ application/       # use-cases, one module per feature
 ├─ domain/            # core business + ports (traits)
 └─ infrastructure/    # adapters (DB, cache, clients, etc.)
proto/                 # protobuf definitions — every file here is compiled by build.rs
```

## Quick Start

### Prerequisites

- Rust (stable, edition 2021).
- `protoc` — required for local builds because `build.rs` compiles every `.proto` in `proto/` via `tonic-prost-build`.
  - macOS: `brew install protobuf`
  - Debian/Ubuntu: `apt-get install protobuf-compiler`
- Docker — only if you switch off the default SQLite backend, or want a real cache or object store locally (see [Capabilities](#capabilities)).

### Run

```bash
cargo run                       # HTTP on 0.0.0.0:$PORT (default 8080)
GRPC_PORT=50052 cargo run       # + inbound gRPC features on 0.0.0.0:50052
LOG_FORMAT=json cargo run       # structured logs (what the Dockerfile sets)
```

Ctrl-C / `SIGTERM` drains both servers: one signal listener, both halves shut
down gracefully, and a gRPC bind failure exits the process instead of leaving
HTTP up with gRPC dead. The drain is bounded at 10s — an idle gRPC channel is
never closed by its client, so without a deadline the process would still be
waiting when Kubernetes SIGKILLs the pod. Exceeding it logs a warning and exits
0 with those connections still open.

### Test

```bash
cargo test
```

CI (`.github/workflows/ci.yml`) runs `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and `cargo test` on every push/PR to `main` (after installing `protoc`). It then runs `cargo check --locked` once per optional feature (`postgres`, `mysql`, `document`, `mssql`, `cache`, `blob`, `analytics`, `timeseries`, `apidocs`) — that is what proves turning a capability on never needs a lock update — plus a separate `cargo audit` job so a RustSec advisory cannot mask the fmt/clippy/test signal.

### Examples

```bash
# local Greeter gRPC server for testing GET /hello/{name} (honors GREETER_PORT, default 50051)
cargo run --example greeter_server

# allocation-per-request measurement through the full router (routing + extractors + handlers + serde + repo)
cargo run --release --example alloc_bench
```

### Docker

```bash
docker build -t hexagonal-rs .
docker run -p 8080:8080 hexagonal-rs
```

The build stage installs `protobuf-compiler` itself, so no local `protoc` is needed just to build the image.

## Extending this project with kodegen

This project was generated by [kodegen](https://github.com/prongbang/kodegen) — keep using the same
binary to scaffold features and switch infrastructure. Full flags, defaults and rationale live in the
kodegen repo's [command reference](https://github.com/prongbang/kodegen#command-reference); this is the
short version for a project that already exists.

```bash
kodegen feature <name> [-t|--transport rest|grpc] [-p|--path .] [--dry-run]
kodegen add <capability> [--orm diesel|seaorm] [-p|--path .] [--dry-run]
kodegen add --list
```

- `kodegen feature order` scaffolds domain/application/infrastructure/api for a new feature and wires
  it up (see [Adding a Feature](#adding-a-feature)). `--transport` defaults to `rest`; `grpc` scaffolds a
  tonic service instead.
- `kodegen add postgres` (etc.) swaps this project's datastore/cache/blob-store/event-sink adapter (see
  [Capabilities](#capabilities)).
- `--dry-run` on either command prints the plan — files to create (`+`) and files to edit (`~`) — and
  writes nothing; it runs the same code path as a real invocation, so a diverged project fails the same
  way with or without it.
- `-p, --path <dir>` runs the command against a project at that path instead of the current directory.

Capabilities, at a glance (`--orm` only applies where marked):

| Capability | Slot | `--orm` |
|---|---|---|
| `postgres` / `mysql` | datastore | `diesel` (default) or `seaorm` |
| `mariadb` | datastore — alias of `mysql` | `diesel` (default) or `seaorm` |
| `timescaledb` | datastore — alias of `postgres`, + hypertable | `diesel` (default) or `seaorm` |
| `mongodb` | datastore | not supported (no ORM) |
| `mssql` | datastore | not accepted — `--orm` errors (no open-source ORM for SQL Server) |
| `redis` | additive (cache) | n/a |
| `s3` | additive (object storage) | n/a |
| `clickhouse` / `influxdb` | event sink | n/a |
| `greptimedb` | event sink — alias of `influxdb` | n/a |

Only one datastore and one event sink can be on at a time (they replace each other); `redis` and `s3`
are additive and sit alongside anything. See [Capabilities](#capabilities) below for what each `add`
touches, its env vars, and its default (server-less) adapter.

## HTTP Endpoints

| Method | Path | Description | Success | Failure |
|---|---|---|---|---|
| GET | `/health` | Liveness: the process is up. Never looks at a backend | `200` `ok` | — |
| GET | `/ready` | Readiness: every real backend's check (`SELECT 1`, `PING`, `HEAD bucket`, ...), run concurrently, 2s each | `200` `{"status":"ok"}` | `503` `{"status":"unavailable","checks":{"<backend>":"ok"\|"<why>"}}` |
| POST | `/users` | Create a user. Body: `{"id": "...", "name": "..."}` | `201` `{"ok": true}` | `400` on empty/too-long `id` or `name` |
| GET | `/users/{id}` | Fetch a user | `200` `User` JSON (`{"id", "name"}`) | `404` if not found |
| GET | `/hello/{name}` | Greet via the outbound gRPC Greeter service | `200` `{"message": "..."}` | `503` if the circuit breaker is open or the upstream is unavailable |

```bash
curl -X POST localhost:8080/users -H 'content-type: application/json' -d '{"id":"u1","name":"Alice"}'
curl localhost:8080/users/u1
curl localhost:8080/hello/world
```

`/health` and `/ready` are the two Kubernetes probes, and they must stay two: a
pod whose database is down should stop *receiving traffic* (`readinessProbe:
/ready`) and not be *restarted* into the same state (`livenessProbe: /health`).
A fresh project registers no check, so `/ready` is `200` with no server around;
each `kodegen add` registers its adapter's in `bootstrap.rs`, and the check *is*
the first connection for the adapters that dial lazily. The failure text is the
`DomainError` (`service unavailable`, `timed out after 2s`, `internal error`) —
never the driver's own, which can carry a connection string; that goes to the
log at `warn`. Set the probe's `timeoutSeconds` above 2. With `GRPC_PORT` set
the same checks also answer `grpc.health.v1` (service `""`, re-evaluated every
10s), for a `grpc:` probe or `grpcurl`. The `Dockerfile` has no `HEALTHCHECK`
— distroless has no shell to run one — so the probes are the orchestrator's job.

Every response carries an `x-request-id`: a caller's own header is passed
through untouched (so an id assigned at the edge survives every hop) and a
request without one gets a fresh uuid. Every request also gets one `INFO` line
when it finishes, carrying `method`, `path`, `request_id`, `status` and
`latency` — as a `tracing` span, so it reads the same in plain text and under
`LOG_FORMAT=json`. Headers and bodies are never logged; they carry credentials.
A handler that outlives `api::REQUEST_TIMEOUT` (30s — well past anything here on
purpose, well under the 60s an idle load balancer gives up at) is dropped and
the caller gets `408 Request Timeout`, still with its id. `api::middleware` is
that whole stack as one function, so a test can wrap a router of its own in it.
With `GRPC_PORT` set the gRPC server gets the same 30s budget and the same
per-request span (no id — gRPC callers carry their own metadata). Both budgets
start once the handler is invoked; hyper's header read and body streaming are
not covered. tonic applies its timeout outside the layer stack, so on expiry a
gRPC caller gets `CANCELLED` ("Timeout expired"), not `DEADLINE_EXCEEDED`, and
nothing is logged — where HTTP gets its `408` and an access-log line.

After `kodegen add scalar`, two more routes exist: `GET /docs` (a Scalar UI,
needs a network for its JS) and `GET /openapi.json` (the spec itself, fully
offline) — see [API documentation](#api-documentation-kodegen-add-scalar).

`DATABASE_URL` per backend — the one that applies is whichever feature is in
`default = [...]` in `Cargo.toml`:

| Backend | `DATABASE_URL` |
|---|---|
| SQLite (default) | `app.db` or `/data/app.db` — a file path, not a URL |
| PostgreSQL | `postgres://app:app@127.0.0.1:5432/app` |
| MySQL / MariaDB | `mysql://app:app@127.0.0.1:3306/app` |
| SQL Server (`mssql`) | not a URL — an ADO.NET connection string: `server=tcp:127.0.0.1,1433;user id=sa;password=…;database=app;encrypt=true;TrustServerCertificate=true` |

Use `127.0.0.1`, not `localhost`, for MySQL/MariaDB: libmysqlclient reads
`localhost` as "connect over the unix socket" and ignores the port, which fails
against a container published on 3306.

## Capabilities

This project ships with SQLite on, and every other backend already declared as
an **optional** dependency. Switching is one command — from
[kodegen](https://github.com/prongbang/kodegen):

```bash
kodegen add postgres      # Diesel + PostgreSQL
kodegen add mysql         # Diesel + MySQL
kodegen add mariadb       # same driver as mysql; MariaDB image
kodegen add timescaledb   # same driver as postgres; + a hypertable migration
kodegen add postgres --orm seaorm   # the same PostgreSQL, on SeaORM (see below)
kodegen add mysql --orm seaorm      # the same MySQL/MariaDB, on SeaORM — no C driver
kodegen add mongodb       # the same UserRepository, on the Mongo driver
kodegen add mssql         # SQL Server / Azure SQL, raw SQL over tiberius (no ORM)
kodegen add redis         # the Cache port + a Redis adapter (Valkey too)
kodegen add s3            # the BlobStore port + an S3 adapter (RustFS/MinIO/AWS)
kodegen add clickhouse    # the EventSink port + a ClickHouse adapter
kodegen add influxdb      # the same port, over line protocol (InfluxDB v2/v3)
kodegen add greptimedb    # the same adapter, GreptimeDB image + URL
kodegen add scalar        # GET /docs + GET /openapi.json, derived from the code
kodegen add --list        # what's supported + what this project has on
```

Two of these are **slots**, and a slot holds one adapter:

- the **datastore** — `postgres`, `mysql`, `mariadb`, `timescaledb`, `mongodb`
  and `mssql` are all adapters of the same `UserRepository`, so they replace each
  other;
- the **event sink** — `clickhouse`, `influxdb` and `greptimedb` are all
  adapters of the same `EventSink`, so they replace each other (`influxdb` and
  `greptimedb` are two names for one of them: same feature, same adapter file).

`redis`, `s3` and `scalar` fill no slot: they sit alongside whatever is on, and
each other. One of each is a legal project
(`--with mongodb,redis,s3,clickhouse,scalar`). `scalar` is the odd one out even
among these three — it has no port and no adapter, just a route and a derived
document (see below), which is also why it takes no `--orm` and needs no env.

### Relational backend

It touches six files:

| File | Change |
|---|---|
| `Cargo.toml` | `default = [...]` gains the new backend feature and loses the old one |
| `src/infrastructure/diesel_db.rs` | **replaced** — `SqliteConnection` becomes `PgConnection`/`MysqlConnection`, and the SQLite WAL/pragma setup goes away |
| `src/infrastructure/diesel_repo.rs` | `save()` becomes the dialect's upsert, and the **test module is replaced** with a `DATABASE_URL`-gated one (a throwaway file is no longer a database) |
| `migrations/*_create_users/up.sql` | the dialect's `CREATE TABLE`, when it differs from what is already there (PostgreSQL's is what the SQLite seed already says, so that one is left alone) |
| `docker-compose.dev.yml` | a dev service with a healthcheck (created if missing) |
| `Dockerfile` | `perl`/`make`/`cmake` on the `apt-get install` line, for building the backend's C driver from source |

Everything else — the ports, `Db::run`, the repositories, `bootstrap.rs`, the
API — is untouched, which is the point of keeping the pool in one file.

Only **one** datastore at a time: `Db` wraps a single connection type, so a
second `add` — another relational backend or `mongodb` — is refused rather than
half-applied. `add` also refuses if
`diesel_db.rs` or the generated test module no longer match what
`kodegen new` wrote — your edits are never overwritten silently. Queries you
added to `diesel_repo.rs` above the test module are kept.

Because the backends are optional dependencies, `Cargo.lock` already pins all of
them and nothing is compiled until its feature is on — `cargo build --locked`
keeps working across the switch, offline included.

Doing it by hand instead: set the feature in `[features] default`, swap
`SqliteConnection` for `PgConnection`/`MysqlConnection` throughout
`diesel_db.rs`, and check the migration's SQL is valid for the dialect. MySQL
in particular **cannot** use `TEXT PRIMARY KEY` — indexing a `TEXT` column needs
a prefix length, so the users table uses `VARCHAR(64)` there. That one fails at
migration time, not compile time.

### Migrations in Kubernetes

The Diesel backends run pending migrations at boot, in `build_pool`. A rollout
starts every replica at once, so on an empty database N harnesses would race
each other — on PostgreSQL that is one pod crash-looping once with `relation
already exists`; on MySQL/MariaDB, where DDL is not transactional, it can be a
half-applied migration. So the run is serialized on the **database's own
lock**: `pg_advisory_lock(hashtext('diesel_migrations'))` on
PostgreSQL/TimescaleDB, `GET_LOCK('diesel_migrations', 3600)` on MySQL/MariaDB
(an hour, not `-1`: MariaDB answers a negative timeout with `NULL` at once
rather than waiting). The second replica waits, then finds nothing pending. The
lock is session-scoped, so a pod killed mid-migration releases it with its
connection. Nothing to configure: N replicas booting together is safe as
shipped.

Session-scoped is also its one requirement. Through a pooler in transaction
mode (PgBouncer `pool_mode=transaction`, ProxySQL) the lock, the migration and
the unlock can each land on a *different* server session, so the lock serializes
nothing and the session that took it holds it until `server_lifetime`. Point
`DATABASE_URL` at the server itself for migrate runs, or use session pooling.

The waiters pay for the lock too: `build_pool` runs before the listener binds,
so a replica queued on it answers neither `/health` nor `/ready` — there is no
open port yet. Size a `startupProbe` to the longest migration you expect
(`failureThreshold × periodSeconds`); without one the liveness probe restarts
the waiters and the rollout never converges.

Two switches for when the replicas should not be the ones applying DDL — the
application role has no `CREATE` rights in production, or a migration is long
enough to trip the readiness/liveness probes of the pod running it:

| Variable | Default | Effect |
|---|---|---|
| `RUN_MODE=migrate` | unset | Do everything the boot does before it listens (for Diesel: the migrations), log, exit 0. Nothing is served. A failed migration is a non-zero exit — and so is a missing datastore URL (`MONGODB_URL` after `add mongodb`, `DATABASE_URL` otherwise), so a typo'd secret fails the Job red instead of quietly migrating the in-memory adapter. |
| `MIGRATE_ON_START=false` | `true` | Skip the migration run at boot: the process only connects. On a database whose schema is behind, the first query fails (a 500 on that request), the process does **not** crash. `/ready` still answers 200 — it checks connectivity, not schema — so the pod takes traffic and 500s on `/users` until the migrate run lands. `RUN_MODE=migrate` ignores this, so a Job and its replicas can share one env. |

The pattern: one `RUN_MODE=migrate` run per rollout, before the replicas.
Either an `initContainer` on the Deployment (every pod runs it; the lock makes
that harmless) or a Job with a hook. Same image, same `DATABASE_URL`:

```yaml
# Deployment: replicas only connect
spec:
  template:
    spec:
      initContainers:
        - name: migrate
          image: ghcr.io/you/app:1.2.3
          env:
            - { name: RUN_MODE, value: migrate }
            - { name: DATABASE_URL, valueFrom: { secretKeyRef: { name: app-db, key: url } } }
      containers:
        - name: app
          image: ghcr.io/you/app:1.2.3
          env:
            - { name: MIGRATE_ON_START, value: "false" }
            - { name: DATABASE_URL, valueFrom: { secretKeyRef: { name: app-db, key: url } } }
```

Migrate mode runs the whole composition root, so every *other* resource's env
has to be there too — `S3_BUCKET` without its credentials fails the migrate run
as readily as the app: `envFrom` the same secret in both containers, so the set
is present or absent together.

For a Job instead of an initContainer, set `activeDeadlineSeconds`: a migrate
run waits on the lock (indefinitely on PostgreSQL, up to an hour on
MySQL/MariaDB), and a deadline is what turns "a stuck holder" into a failed Job
rather than a hung rollout. Roll the schema
forward only — a Deployment keeps old pods serving while new ones come up, so
a migration the previous image cannot live with needs its own two-step.

`sqlite` is one file with one writer and gets the two switches but no lock —
two processes on one file queue on `busy_timeout`, and N replicas over one
SQLite file is not a deployment. The lazy adapters (`--orm seaorm`, `mongodb`,
`mssql`, `clickhouse`) create their schema on the first request with
idempotent statements and a one-shot retry on the loser of a collision, so
they have no boot-time run to move: `RUN_MODE=migrate` exits 0 having done
nothing for them — once its datastore URL is set, which it still checks — and
`MIGRATE_ON_START` is not read.

### The other ORM (`kodegen add <backend> --orm seaorm`)

The relational capabilities take `--orm diesel` (the default, everything above)
or `--orm seaorm`. Same backend, same `DATABASE_URL`, same compose service —
different adapter, and a different set of trade-offs. All four backends:
PostgreSQL and TimescaleDB on `seaorm-postgres`, MySQL and MariaDB on
`seaorm-mysql`.

| File | Change |
|---|---|
| `Cargo.toml` | `default = [...]` becomes `["seaorm-postgres"]` (or `["seaorm-mysql"]`) |
| `src/infrastructure/sea_db.rs` | **created** — the `Db` handle, a lazily opened connection, and the `SCHEMA` applied with it |
| `src/infrastructure/sea_repo.rs` | **created** — the entity and the `UserRepository` adapter |
| `src/infrastructure/mod.rs` | two `#[cfg(feature = "seaorm")] pub mod` lines appended; the Diesel modules stay on disk, gated off |
| `src/bootstrap.rs` | the same three blocks `add mongodb` swaps — the binding stays `db`, and so does its type name |
| `Dockerfile` | **not touched** — sqlx and rustls are pure Rust, so there is no C driver to build |

What you get: no `spawn_blocking`, no r2d2, no blocking pool — sqlx is async to
the socket, so the repository awaits its queries directly. And a build that needs
no `perl`/`make`/`cmake`.

What you give up: **versioned migrations**. `sea_db.rs` carries a `SCHEMA` of
idempotent statements (`CREATE TABLE IF NOT EXISTS`, and on TimescaleDB
`create_hypertable(..., if_not_exists => TRUE)`) applied when the first
connection is opened; `migrations/` is not read on this path. That is fine for a
seed schema. **The first time you change a table that already holds production
data, move to `sea-orm-migration = "1.1"`** (pinned: its 2.x needs sea-orm 2.0
and rustc 1.94), put the statements in the first migration and empty `SCHEMA` —
`CREATE TABLE IF NOT EXISTS` cannot express an `ALTER`, and a startup step that
silently does nothing is worse than one that fails.

Two more things that follow from applying schema at startup:

- **The role in `DATABASE_URL` must be allowed to create tables**, and the tables
  already existing does not excuse it — PostgreSQL checks `CREATE` on the schema
  before it checks whether the object is there. Without it every request fails
  with a 500 (the connection is lazy, so the process still boots), forever. Fix
  it with `GRANT CREATE ON SCHEMA public TO <role>`, or empty `SCHEMA` and own the
  schema out of band.
- **A database that is down costs a request 30 seconds** (sqlx's acquire timeout)
  before its 503, and the failure is not cached — the next request retries.
  `opts.acquire_timeout(...)` in `sea_db.rs` shortens it.

And one thing that follows from MySQL being in the lock at all: `sqlx-mysql`
depends on `rsa`, which carries **RUSTSEC-2023-0071 with no fixed version**.
`Cargo.lock` pins it whether or not `seaorm-mysql` is the selected feature, so
`.cargo/audit.toml` ignores that advisory — the full reasoning is in the file,
and the short version is that the advisory is about RSA *decryption* timing
while `sqlx-mysql` only encrypts, with the public key the server sends during
`caching_sha2_password` auth. Delete the ignore when `rsa` publishes a fix.

Both handles are called `Db`, deliberately: they can never be compiled together
(`src/lib.rs` has a `compile_error!` for the additive-feature case), so sharing
the name is what lets `kodegen feature` builders — `_db: Option<&Db>` — survive a
switch in either direction. When a file has to say which, import it:
`use crate::infrastructure::sea_db::Db;` or `...::diesel_db::Db`. Only the name
is shared — there is no `Db::run` on the SeaORM side.

### TimescaleDB (`kodegen add timescaledb`)

Not a fourth dialect: TimescaleDB **is** PostgreSQL with an extension loaded, so
this is the PostgreSQL capability above — same `postgres` feature, same
`PgConnection`, same upsert, same `DATABASE_URL` — plus two files:

| File | Change |
|---|---|
| `migrations/*_create_users/up.sql` | `CREATE EXTENSION IF NOT EXISTS timescaledb;` first, then the same users table, then an example `events` hypertable |
| `migrations/*_create_users/down.sql` | drops the example table as well as `users`, so a revert can be re-migrated |
| `docker-compose.dev.yml` | `timescale/timescaledb` instead of `postgres` — same service name, port and credentials |

`CREATE EXTENSION` is the migration's first statement because Diesel runs each
migration inside one transaction and TimescaleDB requires it there. The `events`
hypertable — a normal table the extension partitions by time — is an example and
nothing in `src/` reads it; replace it with your own measurement table. Moving an
existing PostgreSQL project across is the image plus that migration, and nothing
in `src/` changes.

An app-side event sink (`kodegen add clickhouse`/`influxdb`/`greptimedb`) is a
different thing and can be added alongside: the hypertable is schema in *this* database, the
event sink is a port to somebody else's.

### Document store (`kodegen add mongodb`)

The same datastore slot as a relational backend, on a driver that is not Diesel:
`UserRepository` is unchanged, so the ports, the application layer and the API
never learn about it.

| File | Change |
|---|---|
| `Cargo.toml` | `default = [...]` loses the relational feature and gains `document` |
| `src/infrastructure/mongo_repo.rs` | the `Mongo` handle + the `UserRepository` adapter |
| `src/infrastructure/mod.rs` | one `#[cfg(feature = "document")] pub mod mongo_repo;` appended — the Diesel modules were already gated on `relational` by the template, and their files stay on disk |
| `src/bootstrap.rs` | `MONGODB_URL`/`MONGODB_DB` replace `DATABASE_URL`; `build_user_service` takes `Option<&Mongo>` |
| `docker-compose.dev.yml` | a `mongo:8` service with a healthcheck (created if missing) |

```bash
docker compose -f docker-compose.dev.yml up -d
MONGODB_URL=mongodb://127.0.0.1:27017 MONGODB_DB=app cargo run
```

The client is dialed **lazily**, through a `tokio::sync::OnceCell` on the first
query: every `mongodb` constructor is `async` while `build_services_from_env()`
is a plain `fn`. A database that is down cannot stop the process from booting,
and a failed dial is not cached — the next request tries again. What it costs is
the first request against an unreachable server: the driver spends its
server-selection timeout (30s by default) looking for one before the request
fails with `503`. Add `?serverSelectionTimeoutMS=2000` to `MONGODB_URL` to fail
faster.

There is no migration to run. `save` upserts on `_id`, which is the domain id,
so it stays insert-or-update and never returns `NotFound`.

Going back is `default = ["sqlite"]` in `Cargo.toml` plus the three Diesel blocks
in `bootstrap.rs`. Nothing has to be deleted: `mongo_repo.rs` is gated on
`document` exactly as the Diesel modules are gated on `relational`, so whichever
one is off is simply not compiled. `relational` also carries the Diesel
dependencies, so with `document` selected the ORM is not in the build graph at
all — `cargo tree -e normal | grep diesel` is empty.

### SQL Server (`kodegen add mssql`)

The datastore slot again, on a driver with **no ORM behind it**: neither Diesel
nor SeaORM supports SQL Server in open source, so this adapter is SQL text with
bound parameters. `UserRepository` is unchanged, so nothing above
`infrastructure/` learns about it.

| File | Change |
|---|---|
| `Cargo.toml` | `default = [...]` loses the datastore feature it had and gains `mssql` |
| `src/infrastructure/mssql_db.rs` | the `Db` handle, the bb8 pool, the startup schema |
| `src/infrastructure/mssql_repo.rs` | the `UserRepository` adapter (`MERGE` + `SELECT`) |
| `src/infrastructure/mod.rs` | two `#[cfg(feature = "mssql")] pub mod` lines appended |
| `src/bootstrap.rs` | the three blocks that named the Diesel handle; `DATABASE_URL` stays |
| `Dockerfile` | `perl make` for vendored OpenSSL, and `ENV SSL_CERT_FILE` in the runtime stage |
| `docker-compose.dev.yml` | a SQL Server 2022 service **and** a one-shot init service |

```bash
docker compose -f docker-compose.dev.yml up -d --wait mssql
docker compose -f docker-compose.dev.yml run --rm mssql-init
DATABASE_URL='server=tcp:127.0.0.1,1433;user id=sa;password=kodeGen!2026;database=app;encrypt=true;TrustServerCertificate=true' cargo run
```

Two commands, not one: `up -d --wait` over the whole file exits **1** even when
everything worked, because `mssql-init` finishes and `--wait` treats a container
that is no longer running as a failed dependency.

`DATABASE_URL` keeps its name — same slot, same switch — but its value is an
**ADO.NET connection string**, not a URL. That is the only shape
`tiberius::Config::from_ado_string` parses, and the shape SSMS and the Azure
portal print.

What the backend forces, none of which is taste:

- **The database is not created by the app.** This image has no `POSTGRES_DB`
  equivalent, so `mssql-init` runs `CREATE DATABASE app` once, and a real
  deployment does the same in its deployment step — an application role is almost
  never granted `CREATE DATABASE`. Without it the first request answers 500 with
  SQL Server's own message in the log ("Cannot open database 'app' requested by
  the login"), immediately rather than after a pool timeout.
- **The schema is applied at startup, not by a migration.** `SCHEMA` in
  `mssql_db.rs` is idempotent — and SQL Server has **no** `CREATE TABLE IF NOT
  EXISTS`, so it is spelled `IF OBJECT_ID(N'dbo.users', N'U') IS NULL CREATE TABLE
  …`. `migrations/` is not read on this path. Columns are `NVARCHAR`, never
  `VARCHAR`: tiberius sends every Rust string as `NVARCHAR`, and the mismatch
  silently costs you the index.
- **`save` is a single `MERGE … WITH (HOLDLOCK);`** — atomic in autocommit, so
  there is no transaction to manage. Both `HOLDLOCK` and the trailing semicolon
  are required; the comment above the constant says what to replace it with if
  `users` ever gains a trigger, a foreign key, a filtered index or an `OUTPUT`
  clause.
- **`ENV SSL_CERT_FILE` is load-bearing.** OpenSSL is linked statically here (the
  runtime image has no libssl), and a vendored build compiles in a certificate
  directory that does not exist at runtime — so without that variable the binary
  cannot verify any certificate, while dev and CI stay green because they connect
  with `TrustServerCertificate=true`. Drop `TrustServerCertificate` in production
  and use a real CA.
- **Host caveats.** There is no arm64 image, so the compose service pins
  `platform: linux/amd64` and is slow on Apple Silicon. And an app built **on
  macOS** cannot reach that container with `TrustServerCertificate=true` at all:
  `native-tls` is Apple's Secure Transport there, tiberius's trust-everything path
  turns SNI off, and Secure Transport refuses the handshake. Use
  `encrypt=DANGER_PLAINTEXT` against your own local container, or run the service
  in a container. On Linux — the runtime image, and CI — it works as written.
- **The driver is the thinnest dependency in this project.** tiberius 0.12.3 was
  released in July 2024 with no release since, and it is the only usable TDS
  implementation in Rust. `cargo audit` runs over `Cargo.lock` in this project's
  CI; if an advisory ever lands on tiberius or on something it pins that a lock
  bump cannot move off, the honest answer is to move off SQL Server, not to add an
  entry to `.cargo/audit.toml`.

Going back is `default = ["sqlite"]` plus the three Diesel blocks in
`bootstrap.rs`. Nothing has to be deleted: both adapters stay on disk behind
their own `cfg`.

### Cache (`kodegen add redis`)

| `src/domain/ports.rs` | the `Cache` port is **appended**: `get`/`set`/`delete`, with an optional TTL |
| `src/domain/mod.rs` | `pub use ports::Cache;` |

### Object storage (`kodegen add s3`)

Additive as well, and one adapter for every S3-compatible server — RustFS,
MinIO, Ceph and AWS S3 differ by an endpoint, not by code:

| File | Change |
|---|---|
| `Cargo.toml` | `default = [...]` gains `blob` (everything else is left alone) |
| `src/domain/ports.rs` | the `BlobStore` port is **appended**: `put`/`get`/`delete`, plus `check_blob_key` |
| `src/domain/mod.rs` | `pub use ports::{check_blob_key, BlobStore};` |
| `src/infrastructure/fs_blobs.rs` | default adapter — one file per key under `BLOB_DIR`, no server needed |
| `src/infrastructure/s3_blobs.rs` | S3 adapter over a client the composition root builds |
| `src/api/mod.rs` | one `blobs: Arc<dyn BlobStore>` field on `Services` |
| `src/bootstrap.rs` | builds the S3 client from `S3_BUCKET`/`S3_ENDPOINT`/credentials, plus a `build_blob_store` builder |
| `tests/blob.rs` | the port's contract, run against **both** adapters (the S3 half is `S3_BUCKET`-gated) |
| `docker-compose.dev.yml` | a RustFS service with a healthcheck (created if missing) |

**Keys are checked before they reach an adapter.** `check_blob_key` requires a
non-empty key of at most 1024 bytes with no backslashes, colons or control
characters, no empty/`.`/`..` segments, and no component the platform reads as a
root, drive or prefix. The filesystem adapter turns a key into a path, so `../`
would walk out of the blob directory and `C:evil.txt` — drive-relative on
Windows — would throw the blob directory away when joined. Doing it in the port
rather than in each adapter is also what keeps the two substitutable: a key S3
would have accepted must not be a key that only works in production.

**Keys must not be prefixes of one another.** `a` and `a/b` are both fine on S3,
which has no directories; on disk `a` has to become a directory to hold `a/b`.
`get` and `delete` are aligned anyway (a directory reads as a miss), but a `put`
of `a` while `a/b` exists fails on the filesystem and succeeds on S3 — so keep
every key a leaf.

**RustFS is not a separate adapter, and neither is MinIO.** They speak the S3
API, so swapping `image: rustfs/rustfs:...` for `image: minio/minio` with
`command: server /data` and `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD` changes
nothing in the generated Rust. On AWS itself, drop `S3_ENDPOINT` and set a real
`S3_REGION`. Credentials come from `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`
rather than the full AWS provider chain — `aws-config` resolves credentials
asynchronously and `build_services_from_env()` is a plain `fn`; if you need IAM
roles or SSO, add `aws-config`, make that function `async` and `.await` the
loader where the client is built.

The bucket itself is not created for you — `tests/blob.rs` creates it because a
test may, but the app assumes it exists, the same way it assumes the database
does. Neither does `docker compose up`, so on a fresh stack `/ready` reports
`s3` as failing until you make it (`aws --endpoint-url http://localhost:9000 s3
mb s3://<bucket>`, or `mc mb`). The readiness check is `HeadBucket`, which AWS
authorizes with `s3:ListBucket` on the **bucket** ARN — a policy granting only
the object ARNs (`arn:aws:s3:::bucket/*`) leaves `/ready` failing on a bucket
the app can otherwise read and write.

### Event sink (`kodegen add clickhouse` / `influxdb` / `greptimedb`)

Additive like the two above, but the backends **share one slot**: the
`EventSink` port has a single adapter, so a project has ClickHouse or a
time-series database, never both. `influxdb` and `greptimedb` are two names for
the time-series one — same cargo feature, same adapter, different image and URL.

| File | Change |
|---|---|
| `Cargo.toml` | `default = [...]` gains `analytics` (ClickHouse) or `timeseries` (line protocol) |
| `src/domain/ports.rs` | the `EventSink` port is **appended**, with `Event` and `check_event` |
| `src/domain/mod.rs` | `pub use ports::{check_event, Event, EventSink};` |
| `src/infrastructure/log_events.rs` | default adapter — writes each event to the tracing subscriber, no server needed |
| `src/infrastructure/clickhouse_events.rs` | ClickHouse adapter over the official client's HTTP interface |
| `src/infrastructure/line_protocol_events.rs` | line-protocol adapter — one HTTP POST, on hyper (already in the graph via tonic) |
| `src/api/mod.rs` | one `events: Arc<dyn EventSink>` field on `Services` |
| `src/bootstrap.rs` | resolves the sink's env once, plus a `build_event_sink` builder in both composition roots |
| `tests/events.rs` | the port's contract, run against **both** adapters (the server half is URL-gated) |
| `docker-compose.dev.yml` | a `clickhouse`, `influxdb` or `greptimedb` service with a healthcheck (created if missing) |

**Write only, and not fire-and-forget.** There is no query method: what you ask
an analytical store is not what you ask a time-series one, so querying is done
directly by whatever needs it, and this port is how the application *records*.
`write` awaits the round trip and returns the failure — there is no queue, no
retry and no backpressure behind it. Batch and `tokio::spawn` if the caller must
not wait; `let _ = sink.write(..).await;` if it can afford to lose events.

**One event is a name, a timestamp and `f64` fields** — no tags, no other field
types. That is the intersection of what both backends take honestly: line
protocol has tags and typed fields, ClickHouse would need a `Map` column and a
schema decision. Put the dimension in the name (`http.requests.checkout`) until a
real requirement says otherwise. `check_event` enforces the rules in the port, in
every adapter including the default one, and its character rule (ASCII letters,
digits and `_-./:`) is what lets the line-protocol adapter skip escaping — a
comma or a space in a measurement changes what the line *means*.

**The default adapter is a log, not a store.** With no URL set, events go to the
tracing subscriber and nothing is queryable. That is the honest default for a
port with no read path; an in-memory buffer would grow without bound while
looking like durability.

**InfluxDB v2, InfluxDB v3 and GreptimeDB are one adapter**, because they accept
the same line protocol over the same kind of endpoint. `bootstrap.rs` appends
`/api/v2/write?bucket=…&precision=ns` to `INFLUX_URL`, so the base address is
what selects the product:

| Server | `INFLUX_URL` | Notes |
|---|---|---|
| InfluxDB v2 | `http://127.0.0.1:8086` | set `INFLUX_ORG`; `INFLUX_BUCKET` is the bucket |
| InfluxDB v3 | `http://127.0.0.1:8181` | `INFLUX_BUCKET` is the database; org is ignored |
| GreptimeDB | `http://127.0.0.1:4000/v1/influxdb` | `INFLUX_BUCKET` is the database and it must already exist — the server creates *tables* on write but never a database, and `public` is the one a fresh server has. `INFLUX_ORG` is ignored, and `INFLUX_TOKEN` is unused unless authentication is on (then it is `<user>:<password>`, not a bare token) |

Swap the image in `docker-compose.dev.yml` and nothing in the generated Rust
changes — the same relationship Valkey has to `redis` and MinIO to `s3`.
`kodegen add greptimedb` is that swap made for you.

**Every write has a 5s budget**, because neither hyper nor the ClickHouse client
has a default timeout: a sink that accepts the connection and then says nothing
would otherwise hold the caller, and the request it is on, indefinitely. A
timeout surfaces as `DomainError::Unavailable`, the same as a refused connection.
The Redis adapter is deliberately not wrapped this way — its connection manager
is unbounded too, but it owns its own reconnect loop and a cache call is not the
thing that must not hang.

**Both adapters speak plain HTTP.** For a managed endpoint on https, put it
behind a TLS-terminating proxy, turn on the `clickhouse` crate's `rustls-tls`
feature, or swap `build_http()` in `line_protocol_events.rs` for a `hyper-rustls`
connector. The line-protocol adapter is written on hyper rather than a client
crate because `tonic` already puts hyper in the dependency graph: the whole
`timeseries` feature adds **nothing** to `Cargo.lock`.

ClickHouse creates its table on the first write (`CREATE TABLE IF NOT EXISTS
events … ENGINE = MergeTree`) — it is not this project's relational database, so
it has no `migrations/` step. The table is one row per field, which keeps the row
type a plain `derive(Row)`; a wide table is the right answer once you know your
fields, and `clickhouse_events.rs` is where you would make that change.

### API documentation (`kodegen add scalar`)

No port, no adapter, no slot — this one is a route and a document, not a piece
of infrastructure, so it sits next to anything and never conflicts.

```
Cargo.toml                              default = [...] gains "apidocs" (utoipa/utoipa-scalar were already optional deps)
src/api/openapi.rs                      created — the ApiDoc derive + GET /docs + GET /openapi.json
src/api/mod.rs                          .merge(openapi::routes()); #[cfg_attr(..., utoipa::path)] on health and ready, ToSchema on ErrorRes and ReadyRes
src/api/user.rs                         same cfg_attr treatment on create_user/get_user/CreateUserReq
src/api/hello.rs                        same cfg_attr treatment on say_hello
src/domain/model.rs                     ToSchema on User
tests/apidocs.rs                        created — GET /openapi.json parses + covers the shipped routes, GET /docs is reachable
```

```bash
kodegen add scalar
cargo run
curl localhost:8080/openapi.json | jq .paths    # every annotated route, offline
open http://localhost:8080/docs                 # needs a network — see below
```

**The spec is derived from the code, not hand-maintained JSON.** Every handler
and DTO the template ships is annotated with
`#[cfg_attr(feature = "apidocs", utoipa::path(...))]` /
`#[cfg_attr(feature = "apidocs", derive(utoipa::ToSchema))]` **unconditionally**
— whether or not `apidocs` is on — and `kodegen feature <name>` carries the same
annotations on every handler it scaffolds, in either order relative to
`add scalar`:

- `kodegen feature order` then `kodegen add scalar`: the new handlers are
  already annotated, so `add scalar` finds them and lists them in
  `paths(...)` from the start.
- `kodegen add scalar` then `kodegen feature order`: `add_feature` sees
  `src/api/openapi.rs` on disk and inserts the new feature's two paths above
  the `// kodegen:openapi:paths` marker that file carries.

A route added **by hand**, without the attribute, is invisible to the spec —
there is no compiler check for "every route is documented", so add the
attribute and one line in `paths(...)` (or run `kodegen feature`, which never
forgets it) whenever you add one yourself.

**`GET /docs` needs a network; `GET /openapi.json` does not.** `utoipa-scalar`
serves a small HTML page whose `<script>` loads the Scalar UI from
`cdn.jsdelivr.net` — `build`, `cargo test` and `GET /openapi.json` never touch
the network, but the `/docs` page itself renders blank without one. Upgrade
path if that matters for your deployment: swap `Scalar::with_url(...)` in
`openapi.rs` for `Scalar::new(spec).custom_html(...)` with a vendored copy of
`@scalar/api-reference` (~1.5 MB) — not done here, because it would grow the
binary and every generated project for a need nobody has stated yet.

**Both routes ship in a production build unless you turn them off.** `apidocs`
is a `default = [...]` feature like any other: drop it and both routes — and
every `cfg_attr`-gated line — compile out completely, not just stop being
registered. Do that before shipping anything you would not want the API
surface (paths, request/response shapes, tags) publicly readable for, or put
`/docs` and `/openapi.json` behind the same auth/ingress rule as the rest of
the API.

**Schemas are collected automatically.** `#[openapi(paths(...))]` only lists
functions; utoipa 5 walks each one's `request_body`/`responses` recursively and
adds `CreateUserReq`, `ErrorRes`, `ReadyRes`, `User` (and whatever a scaffolded
feature adds) to `components.schemas` without a `components(schemas(...))` list
to keep in sync by hand. `info.title`/`info.version` come from `Cargo.toml`'s own
`[package] name`/`version` — no placeholder to forget either.

## Outbound gRPC + Circuit Breaker

- The `Greeter` port (`src/domain/ports.rs`) is implemented by `GrpcGreeter` (`src/infrastructure/grpc_greeter.rs`), which wraps a generated `GreeterClient` (from `proto/greeter.proto`, compiled by `build.rs`).
- The underlying tonic `Channel` is wrapped with a tower `BreakerLayer` (`src/infrastructure/circuit_breaker.rs`), backed by [`recloser`](https://docs.rs/recloser). The default breaker (`default_breaker()`) opens once ≥50% of the last 100 calls fail, and after a 30s cooldown allows a half-open trial call through.
- The tonic `Endpoint` is configured with a 2s connect timeout and a 5s request timeout (`GrpcGreeter::connect_lazy`).
- When the circuit is open, calls are rejected before hitting the network and mapped to `DomainError::Unavailable`; the same mapping applies to genuine gRPC `Unavailable`/`DeadlineExceeded` statuses. The `api` layer turns `DomainError::Unavailable` into HTTP `503`.
- Swapping the greeter implementation or tuning the breaker/timeouts only touches `bootstrap.rs` (`build_greeter()`) — `domain` and `api` stay unaware of gRPC/recloser.

## Responsibilities

### `main.rs` — Entrypoint
- Starts the runtime (logging/tracing/Tokio).
- Binds the TCP listener and calls `axum::serve`; when `GRPC_PORT` is set it also serves a tonic server with `bootstrap::grpc_routes(&services)`. Both run under one `try_join!` and one shutdown signal, so either one's error ends the process and either one's failure is not silent.
- Contains no business logic or wiring details.

### `bootstrap.rs` — Composition Root
- Builds concrete adapters (e.g., Diesel/SQLite vs. in-memory), services, and the HTTP router/state.
- `build_services_from_env()` resolves shared resources once (e.g. the `Db` pool from `DATABASE_URL`), then one `build_<feature>_service(db)` builder per feature picks its adapter — adding a feature adds one builder and one `Services` field, nothing multiplies.
- `grpc_routes(&services)` collects inbound tonic services (one `.add_service(...)` per gRPC feature); `main.rs` serves it when `GRPC_PORT` is set.
- The only module allowed to import **everything** (api + application + domain + infra).
- Great place to switch implementations by config/env/feature flags.
- Tests build on top of it: call `bootstrap::build_services()` to get real defaults (in-memory repo, `GrpcGreeter`), then swap in a fake port implementation before passing the services to `api::router()`. See `tests/api.rs` (`FakeGreeter`) for the pattern. One test also asserts the response JSON's exact key set (`["id", "name"]`) as a trip-wire: if the domain `User` gains a field, that assertion fails instead of silently widening the public API — the fix is a response DTO, not loosening the test.

### `api/` — Delivery Layer
- One module per feature: `<feature>.rs` holds that feature's axum `routes()` + handlers; `<feature>_grpc.rs` holds a tonic adapter registered in `bootstrap::grpc_routes`. `mod.rs` just owns `Services` and assembles `router()` from `.merge(<feature>::routes())` lines.
- Handlers pull only the dependencies they need via `State<…>` (often with `FromRef`).
- Maps domain/application errors into HTTP status codes (`to_http_err`) or gRPC `Status` (`to_status` in each `*_grpc.rs`).
- No database or business rules here.

### `application/` — Use‑Cases
- Orchestrates flows across domain objects and ports (e.g., `CreateUser`, `GetUser`).
- Depends on **domain ports (traits)** only; unaware of specific databases/HTTP.
- A natural place for transaction boundaries and cross-entity workflows.

### `domain/` — Core
- Entities, value objects, domain services, and domain errors.
- **Ports (traits)** such as `UserRepository` are defined here, each documenting a behavioral contract — e.g. `UserRepository::save` is an upsert and never returns `NotFound`; `get` returns `NotFound` when the id is absent, not an empty/default value. Adapters must honor the documented contract so they stay substitutable.
- `kodegen add redis` appends a `Cache` port on the same terms, and its contract deliberately differs where the semantics do: a cache miss is `Ok(None)`, never `NotFound`, and `delete` on an absent key is `Ok(())`. `tests/cache.rs` runs those assertions against every adapter, which is what keeps "substitutable" a fact rather than a claim.
- `kodegen add s3` appends a `BlobStore` port the same way: `get` on a missing key is `Ok(None)` (a blob store has no `NotFound`), `put` overwrites, `delete` is idempotent, and `check_blob_key` lives beside the trait so every adapter refuses the same keys instead of each one deciding for itself. `tests/blob.rs` runs one contract against both adapters.
- `kodegen add clickhouse` / `influxdb` / `greptimedb` append an `EventSink` port, which is the one that is deliberately **write-only**: an analytical query and a time-series query are not the same interface, so querying stays outside the port and this is how the application records. `write` is not fire-and-forget either — it awaits the round trip and returns the failure, because a queue that silently drops is a decision for the caller, not for the port. `check_event` sits beside the trait for the same reason `check_blob_key` does, and `tests/events.rs` runs one contract against both adapters.
- Pure business rules; framework‑agnostic; minimal dependencies.

### `infrastructure/` — Adapters
- Implements domain ports: DB repositories, caches, MQ, external clients (gRPC), logging, config, migrations.
- Swappable without touching `domain`/`application` code.
- `UserRepository` ships two adapters: `in_memory_repo::InMemoryUserRepository` (default) and `diesel_repo::DieselUserRepository`, selected at startup by setting `DATABASE_URL` (see `bootstrap::build_router`).
- After `kodegen add redis` the `Cache` port has the same pair: `in_memory_cache::InMemoryCache` (default) and `redis_cache::RedisCache`, selected by `REDIS_URL`. The Redis connection is created lazily by the composition root, so an unreachable cache delays nothing at startup and reconnects on its own — but a command issued while it is down returns `DomainError::Other`, it is not silently swallowed.
- After `kodegen add s3` the `BlobStore` port has its own pair: `fs_blobs::FsBlobStore` (default — one file per key under `BLOB_DIR`) and `s3_blobs::S3BlobStore`, selected by `S3_BUCKET`. The S3 client is built once by the composition root, so the adapter never reads `S3_ENDPOINT` itself; an unreachable server surfaces as `DomainError::Unavailable` (a 503), while anything the server actually answered — no such bucket, access denied — stays `Other`.
- After `kodegen add clickhouse`, `influxdb` or `greptimedb` the `EventSink` port has the same pair: `log_events::LogEventSink` (default — the tracing subscriber, so nothing is queryable and nothing survives the process) and one of `clickhouse_events::ClickhouseEventSink` / `line_protocol_events::LineProtocolEventSink`, selected by `CLICKHOUSE_URL` / `INFLUX_URL`. Same error split as the others: a sink that cannot be reached is `Unavailable` (a 503), a sink that answered — a bad token, an unknown bucket, a rejected point — is `Other`.
- Diesel/SQLite plumbing shared by every repository lives in `diesel_db.rs`, not in the repository itself: `build_pool(url)` runs the embedded migrations and, on a single setup connection, switches the database file to `WAL` mode once; the resulting r2d2 pool is wrapped in a cheap-to-clone `Db` handle whose `run(closure)` does the `spawn_blocking` + connection checkout + error mapping every repository needs. `DieselUserRepository::new(db: Db)` just takes that handle, so a future repository shares the same pool by cloning `Db` rather than re-deriving pool/pragma logic.
- Every pooled connection also sets `PRAGMA busy_timeout` and `PRAGMA synchronous = NORMAL` on acquire: SQLite allows only one writer at a time, so without WAL + `busy_timeout` concurrent writers fail immediately with `SQLITE_BUSY` instead of waiting their turn. **This paragraph and the one above describe the default SQLite backend** — on PostgreSQL or MySQL (see [Capabilities](#capabilities)) `diesel_db.rs` has no pragma customizer at all, because neither has SQLite's single-writer problem; `Db`, `Db::run` and every repository stay exactly the same.
- The composition root (`bootstrap.rs`) is the only place that builds the pool and constructs `DieselUserRepository`; repositories never see `DATABASE_URL` or the pool directly.
- Moving to Postgres/MySQL later swaps the `diesel` backend feature and the connection type inside `diesel_db.rs` — the port, the repositories and every call site stay as they are. `kodegen add postgres` does it for you; see [Capabilities](#capabilities).
- After `kodegen add <backend> --orm seaorm` the same two paragraphs describe `sea_db.rs` instead, with two differences that matter: there is no pool to build at startup (the connection is opened on the first query, and the schema in `SCHEMA` goes with it) and there is no `Db::run`, because sqlx is async to the socket — `SeaUserRepository` awaits its queries directly, with no `spawn_blocking` and no blocking pool. The handle is still called `Db` and is still built only by the composition root, so everything above `infrastructure/` reads the same on either ORM.

## Dependency Direction

```
api  ─▶  application  ─▶  domain
                       ▲
                       └── infrastructure (implements domain ports)
bootstrap depends on all to assemble the app
```

- **Only the composition root** (`bootstrap.rs`) wires concrete implementations together.
- **api** depends on **application**, **application** depends on **domain** (ports), and **infrastructure** implements those ports.

## Typical Request Flow

`POST /users` → `api` handler → `application` use‑case → domain validation → call `UserRepository` (port) → `infrastructure` repository hits DB → result mapped back to HTTP.

A gRPC feature is the same flow with a different first hop: `Create` RPC → `api/<feature>_grpc.rs` adapter → the **same** `application` use-case; errors map to `tonic::Status` instead of HTTP codes.

## Adding a Feature

If this project was generated with [kodegen](https://github.com/prongbang/kodegen), the whole
checklist below is automated: `kodegen feature orders` creates every file, wires it up, and
leaves working `POST /orders` + `GET /orders/{id}` routes plus an integration test.
`kodegen feature orders --transport grpc` scaffolds the same domain/application/infrastructure
layers but delivers them as a tonic service instead: a `proto/orders.proto`, an
`api/orders_grpc.rs` adapter registered in `bootstrap::grpc_routes`, and a client-based
integration test. Serve gRPC features with `GRPC_PORT=50052 cargo run`.

Manually, follow the dependency direction, inside out. Example: `orders`.

1. **`domain/`** — add the entity to `model.rs`, the port trait (e.g. `OrderRepository`) to `ports.rs`, re-export both in `domain/mod.rs`. Add a `DomainError` variant only if none fits.
2. **`application/orders.rs`** — define `OrderService` (trait) + `OrderServiceImpl` (impl over the port). Register in `application/mod.rs`: `pub mod orders;` + re-export.
3. **`infrastructure/`** — implement the port: `orders_repo.rs` (start in-memory; a Diesel one reuses `Db` by cloning it). Register in `infrastructure/mod.rs`.
4. **`api/orders.rs`** — handlers + a `OrderSvc(Arc<dyn OrderService>)` wrapper with `FromRef<Services>` + its own `routes()`. Then in `api/mod.rs`: add `pub mod orders;`, one `order` field on `Services`, and one `.merge(orders::routes())` in `router()` (or `.nest("/orders", …)` for a prefix).
5. **`bootstrap.rs`** — add a `build_order_service(db: Option<&Db>)` builder (picks the adapter, reuses the pool via `db.clone()`) and set the new field in `build_services_from_env()`/`build_services()`. For a gRPC feature, also add `.add_service(...)` in `grpc_routes()`. Don't delete the `// kodegen:*` comments — `kodegen feature` inserts at them, and without them it falls back to matching the `user:` lines (so removing the `user` feature would break the scaffolder).
6. **`tests/`** — hit the new routes through `bootstrap::build_services()`, swapping in a fake port impl where needed (see `FakeGreeter` in `tests/api.rs`).

Each step touches one file per layer; nothing existing changes shape — `Services` gains a field, `router()` gains routes, everything else is new files.

## Production Notes

- **Testability:** domain/application can be unit‑tested with mocks; API/infra with integration tests.
- **Swappable adapters:** change DB/clients in `infrastructure/`, adjust wiring only in `bootstrap.rs`.
- **Clear boundaries:** each layer has a single responsibility; accidental cross‑layer imports are easy to spot.
- **`dyn` services, measured:** `Services` holds `Arc<dyn UserService>` / `Arc<dyn Greeter>` so adding a feature never grows generic signatures. The vtable cost is not measurable here: allocations per request are identical to a fully-generic variant (`#[async_trait]` already boxes every call), and `wrk` throughput differs by less than run-to-run noise (±2%). If you strip `async_trait` and need every nanosecond, making `Services` generic again is a local change to `api/mod.rs` + `bootstrap.rs`.
- **State cloning:** prefer storing types that are cheap to clone (e.g., `diesel::r2d2::Pool` and `tonic::transport::Channel` are already cheap/Arc-backed — see `Db` in `diesel_db.rs`). Wrap custom non‑clone resources in `Arc<T>` only when necessary.
- **`GET /docs` / `GET /openapi.json` (after `kodegen add scalar`) are on by default**, gated only on the `apidocs` cargo feature — no env kill switch. They expose every annotated route, request/response shape and tag; drop `"apidocs"` from `default = [...]` in `Cargo.toml` before a build you don't want that public, or put both routes behind the same auth/ingress rule as the rest of the API. See [API documentation](#api-documentation-kodegen-add-scalar) for the full trade-off.

## Getting Started (wiring, simplified)

The real wiring lives in `src/bootstrap.rs` and `src/main.rs`; this is the shape of it,
trimmed for illustration (see those files for the actual code, including the
greeter/circuit-breaker wiring, `PORT`/`GREETER_ADDR` env handling, and graceful shutdown):

```rust
// bootstrap.rs
pub fn build_router() -> axum::Router {
    api::router(build_services_from_env())
}

pub fn build_services_from_env() -> api::Services {
    // shared resources are resolved once; each feature builder picks its adapter
    let db = std::env::var("DATABASE_URL")
        .ok()
        .map(|url| Db::new(build_pool(&url).expect("diesel pool init failed")));
    // kodegen:resources

    api::Services {
        user: build_user_service(db.as_ref()),
        greeter: build_greeter(),
        // kodegen:services:env
    }
}

// one builder per feature: picks Diesel when a Db is available, in-memory otherwise
fn build_user_service(db: Option<&Db>) -> Arc<dyn UserService> {
    let repo: Arc<dyn UserRepository> = match db {
        Some(db) => Arc::new(DieselUserRepository::new(db.clone())),
        None => Arc::new(InMemoryUserRepository::new()),
    };
    Arc::new(UserServiceImpl::new(repo))
}
```

```rust
// main.rs
use tokio::net::TcpListener;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let app = crate::bootstrap::build_router();
    let listener = TcpListener::bind("0.0.0.0:8080").await?;
    axum::serve(listener, app).await?;
    Ok(())
}
```

## Tips

- Use `FromRef` (or small newtype wrappers + `FromRef`) so each handler requests only the dependency it needs.
- Put environment/config parsing in `bootstrap.rs`; keep `api/application/domain` framework‑agnostic.
- For multiple binaries (API, worker, migrator), create `src/bin/<name>.rs` and share `bootstrap` helpers.
